The project timeline

From a Python prototype (2026-05-15) to a deployed AI assistant (2026-10-01). It is told in seven eras, and each era says what happened, what the team knew at the time, what it cost, how git was used, and the lesson for next time.

The project in one paragraph

Clean Earth Rovers (CER) sells water-quality sensor pods ("DataPods") that measure six things: temperature, dissolved oxygen (DO), ORP, conductivity, pH and turbidity. Its customer dashboard had an assistant called Gilligan. This repository, cer-demo, is a new Gilligan "brain". It answers questions using two sources: a library of water-science documents (via retrieval), and live sensor readings (via tools). It also writes PDF reports. Most of the hard engineering went into evaluation, which means proving with numbers that the answers are correct and grounded in sources.

Era 1: The prototype

2026-05-15 to 2026-07-16 · about 10 commits

It started as one commit of 2,729 lines: a Python FastAPI backend, Postgres with pgvector for "hybrid RAG" (keyword plus vector search), Docker, tests and a static HTML page. Over the following weeks came setup instructions, a rule to refuse out-of-scope questions, and a timeline. Then little happened until July.

In July the decisive question was gate ◆G1, the target stack. Three options were weighed: (A) keep the Python demo, (B) a hybrid, or (C) port everything to Node/Express + Firestore so it matched CER's existing server and dashboard. C was chosen. On Jul 12 the team reverse-engineered coding conventions from CER's two repositories. On Jul 16 it deleted the Python backend and scaffolded the new TypeScript service.

What we knew then

The product had to live inside CER's stack, which is JavaScript and Firestore on Google Cloud. A Python service with Postgres would have been a second stack for CER's team to run. Nobody yet knew whether RAG was even the right approach for this corpus.

Lesson

  • Good: the team chose the stack by asking who has to operate it. That is the right question for a small company.
  • Good: before deleting the Python code, its behaviour was written down in docs/migration/MIGRATION_SPEC.md, so no logic was lost in the port.
  • Next time: settle the deployment target in week one. The prototype showed the idea worked, but nearly all of its code was thrown away.

Git lens: commits that tell a story

The first commit, init baseline: docker + fastAPI + hybrid RAG + tests, holds 23 files at once. Big-bang commits like that are normal for an import, but you can't review them, and later git blame points every line at one useless commit.

The Jul 16 migration was done well. It used three separate commits: remove the legacy code, scaffold the new service, write the docs. Splitting work like this lets you revert one part without undoing the rest.

# See any commit's files without checking it out
git show --stat $(git rev-list --max-parents=0 dev)   # the very first commit
git log --reverse --format='%ad %s' --date=short | head  # history, oldest first

Best practice: one logical change per commit, and a subject that says what changed. The early messages (added: set up instructions) later gave way to a better style (feat(retrieval): add firestore-direct adapter…, and later plain sentences such as Default the alpha-ratio filter off so the corpus cannot silently re-filter). The last style is the most useful, because the subject explains why.

Era 2: The bake-off

2026-07-28 to 2026-08-29 · about 170 commits

The big open question was ◆G7: how should the model get the documents? There were two families:

  • Direct-feed: paste source text straight into the prompt. Simple, but every question pays for a lot of input tokens.
  • RAG (retrieval-augmented generation): cut the documents into chunks, turn each chunk into an embedding (a list of numbers that captures meaning), search for the chunks closest to the question, and send only those. Each question is cheaper, but there are fixed costs for indexing.

Rather than argue, the team measured it, which was the right instinct. The work built:

  • a retrieval interface with swappable "arms": firestore-direct, pgvector-rag, firestore-vector, and later local-vector and hybrids
  • a capture runner that records every answer with its exact context, token counts and timing
  • a cost model with a break-even curve
  • blind human grading packets
  • an offline retrieval harness
  • on Aug 26, a Tier 2 LLM judge: a second model that grades answers

The product grew at the same time: a sensor tool reading live pods through CER's device API (Aug 11-16), the demo frontend (Aug 18-19), report generation (Aug 20, merged from a collaborator's pull request), a usage quota (Aug 21), and a corpus expanded to 18 documents and trimmed to 15.

On Aug 26, ◆G7 was split. The retrieval half was "closed" on firestore-direct, and the quality floor was re-filed as a deploy blocker.

What we knew then

The numbers looked meaningful: three arms, two passes each, priced and graded. The comparison seemed to show that extra chunks dilute answers. What the team didn't fully take in was that every capture used gpt-oss-20b, a placeholder model, and that 53-59% of its answers contained an ungrounded claim.

Where time was wasted (blunt)

  • About 4-5 weeks of eval results were later discarded. All 224 transcripts and the grading packets were archived on Sep 1. The instruments survived: the runner, cost model, harness and judge. The numbers did not. In the bake-off doc's own words: "The instruments were kept; the numbers were not."
  • The order of measurement was wrong. Retrieval arms were compared while the generator was broken. If the model ignores its sources half the time, a better retriever can't show up in the scores. A gold-context arm (give the model exactly the right passages, to measure its ceiling) would have exposed this in a day. It wasn't built until Sep 9.
  • The question set couldn't test retrieval. 27 of its 30 fixtures were answerable from 4.4% of the corpus, and the whole "deep in the manual" class had 3 questions. A mean over 3 samples on a 0-2 scale has a standard error of about 0.43, which is too noisy to conclude anything.
  • Over-control caused a deadlock. The system prompt was pinned so that arms stayed comparable, which meant generation quality couldn't be improved without voiding the captures. Splitting the gate was a way out, but it recorded a provisional result as "CLOSED".

Lesson for an ML engineer

  • Measure the ceiling before comparing components. Fix or bound generation first, then compare retrieval.
  • Evaluate on the model you will ship. Results on a stand-in model rarely transfer.
  • Size the eval set for the decision. Work out the noise (standard error) per class before trusting class means.
  • Good: setting pass/fail thresholds before running anything (Jul 30: "fix the quality floor and latency ceiling before any arm runs") is real scientific discipline, and it carried into the rebuild.

Git lens: evidence in git, pull requests, and the pickaxe

Transcripts were committed as data (test(eval): add bake-off sweep transcripts, 3 arms x 2 passes). That's unusual and deliberate. A captured model answer can't be reproduced exactly, so git is the lab notebook.

The only pull requests in the history (#1-#4, Aug 20) brought in the report generator from a collaborator. After that, work went to dev directly or through local merges. For a team, PRs are the review point; for a solo project driven by agents, the review happened in chat instead.

Useful trick, the pickaxe -S: it finds the commits that added or removed a string. I used it in today's doc audit to find when env vars appeared:

git log --reverse -S"QUERY_REWRITE" --format='%h %ad %s' --date=short -- src | head -1
# -> the commit that introduced QUERY_REWRITE (2026-09-26)

Era 3: The reset

2026-08-30 to 2026-09-02 · four days

The team stopped and wrote docs/EVAL_REBUILD.md, which opens with three reasons the previous evaluation "produced a decision that does not hold up": the confounded comparison, the gate closed in the wrong order, and the placeholder model. A fourth problem was that the fixture set couldn't do its job. Then they rebuilt from scratch, in four steps:

  1. Freeze chunking (Aug 31), because changing chunks invalidates every label.
  2. Claim inventory (Sep 1): an agent read all 451 chunks and listed 2,250 factual claims they support, so questions could be written from what the corpus actually says.
  3. Wave 1 fixtures (Sep 1): 46 conversations of 2 turns each, in seven classes (cross-document, deep-in-manual, definitional, follow-up, precedence, probe-calibration, refusal).
  4. Decontamination: check that questions don't copy the source wording (22.8% document-level against a bar of under 40%). A question that copies its source chunk is trivially easy for search to find, so it inflates retrieval scores.

It also chose the three model roles: Claude writes the fixtures, a different model family is the judge (deepseek-v4-flash-0731), and a third family generates answers. That way no model grades its own work.

What we knew then

By now the team knew the old numbers were unreliable. They didn't yet know which model would ship, or whether the corpus was right. Both changed later.

Lesson

  • Good: this is the most transferable moment in the project. The team admitted the eval was broken, wrote down exactly why, and rebuilt it with guards against each failure. Interviewers love this story, because most teams never admit it.
  • Good: the judge was chosen with evidence (agreement with human grades), and it's called through an API with a pinned model, temperature 0 and a JSON schema. It is never called through a chat CLI.
  • Next time: do this design work first. Almost none of it depended on the bake-off's results.

Git lens: archive with tags, not with deletion

556 old eval files (about 20 MB) were removed from the working tree, but nothing was lost. The pattern (shown in general form below) is to tag the commit that still has them, delete them, and record the tag in docs/ARCHIVED.md. Later you can read any archived file without restoring it:

git tag eval-archive-2026-09-01            # bookmark the commit that still has the files
git rm -r eval/transcripts eval/grading    # remove them from the tree
git show eval-archive-2026-09-01:eval/grading/warm/scores.csv   # read one later

This repo has 9 archive or recovery tags. Trade-off: the files stay in git history forever, so the clone doesn't shrink. That's fine at 20 MB, but large binary data belongs in object storage or Git LFS.

Era 4: Rebuilding the instruments

2026-09-03 to 2026-09-16 · about 80 commits

  • Sep 9: the refusal gate now reads a fixture flag instead of guessing from rubric text. Labels are resolved from the claim inventory. The gold-context arm is added; this is the ceiling measurement that was missing in Era 2.
  • Sep 10: a meeting with the operator (CER) brought turbidity clarity bands and an audit log of every answer.
  • Sep 13, a big day:
    • The operator's "source of truth" document was removed from the corpus and the prompt's range table deleted, because the ranges were vetoed. Pod limits now come from each pod's own registry settings through a tool.
    • Quote-carrying citations arrived: the model must cite as 【n†"quote"】, so a gate can check the quote really appears in excerpt n.
    • The fixture set became 45 conversations and 90 turns.
    • Dated hand-off documents were replaced by one living docs/STATUS.md.
  • Sep 13-16: git and delegation rules were turned into project skills. The demo frontend was made to match the real dashboard, and starter prompts were removed.

What we knew then

The eval had its instruments back but no fresh baseline. The first post-rebuild capture (Sep 14) was later voided because the fixtures and prompt kept changing under it.

Where time was wasted (blunt)

  • Documentation overhead. 38% of all commits touch only docs. STATUS alone was rewritten 44 times. Dated hand-offs were written and then archived in batches (Aug 30, Sep 13, Sep 23). For an AI-agent workflow, docs are working memory between sessions, so some of this is necessary. Much of it, though, re-described state that git already records.
  • Corpus churn. The corpus went from 8 documents to 18, then 15, then 14 (Sep 13), then 16 (Sep 27). Every change risks invalidating labels and captures. Settling with the domain expert which sources are authoritative before building labels would have saved several re-ingest cycles.

Lesson

  • Good: making citations checkable by machine (quote plus excerpt id) turns "is this grounded?" from opinion into a test.
  • Good: moving numeric thresholds out of the prompt and into per-pod data is the right design. The prompt shouldn't hard-code facts that differ per customer.
  • Next time: one living status file from day one, and keep it short.

Git lens: guardrails for agents

On Sep 13 the git rules moved into a git-plan skill. Agents may run reversible git commands freely, but must ask before anything irreversible: reset --hard, push --force, branch -D, clean -f. That split is a good rule for humans too.

git merge --ff-only feature   # refuses unless it's a pure fast-forward: no surprise merge commits
git branch -d feature         # lowercase -d refuses to delete unmerged work; -D forces it
git add path/one path/two     # stage explicit paths, never "git add -A" in a shared tree

Era 5: The pivot and the incident

2026-09-17 to 2026-09-22

Sep 17: the goal changed. The driving track became the Gilligan release: replace the dashboard's assistant with this service by Sep 30. The architecture, roadmap (R1-R3) and decisions D1-D12 were written up, and questions went to the supervisor.

Sep 19: the security incident. CER's own upstream repositories had malware committed into tooling config files. It was obfuscated JavaScript placed after several hundred spaces on the same line, so it was invisible in editors and GitHub diffs. It runs automatically on next dev, next build and npm test. It ran on the developer machine and stole credentials. The machine was wiped and rebuilt. cer-demo itself was never infected (verified twice).

Sep 21-22: recovery. About 12 commits from Sep 17-19 had been committed but never pushed, and were lost with the wipe. They were rebuilt from saved agent session transcripts (tag old-machine-recovery-2026-09-19). The corpus PDFs were re-sourced, and the OCR cache for one scanned document was regenerated, which moved 12 chunk ids.

What it cost

Roughly 3-4 days of recovery work in the most time-critical fortnight, plus key rotation. The permanent residue is in every CLAUDE.md and STATUS file: never check out main/develop upstream, and scan after every fetch.

Lesson

  • Push often, even to a private branch. A commit that exists on one machine isn't backed up.
  • Treat third-party repos as untrusted code, even your employer's. Config files that tools load automatically (jest.config.js, postcss.config.js) run code without any install step.
  • Good: saved agent transcripts turned out to be a backup of the work itself. The incident write-up was reconstructed from them too.

Git lens: hiding in plain sight

# the scan this project runs after any clone, fetch, pull or branch switch:
grep -rlE ' {200,}' --exclude-dir=node_modules --exclude-dir=.git .
# lists any file with a run of 200+ spaces, which is where the payload hid

git diff --ws-error-highlight=all   # shows whitespace in diffs
git log --format='%h %an %ae %s' -- jest.config.js   # who last touched a config file?

Best practice: review dependency and config changes as carefully as code. Protect main with required reviews, and use commit signing so you know who authored what.

Era 6: The sprint

2026-09-23 to 2026-09-28 · 270 commits in one week

The eval work (called R4 in the release plan) ran in parallel with release engineering. The eval track went like this:

Release engineering ran alongside:

  • supervisor answers on scope, limits and data policy
  • a shared service key between CER's server and this service
  • a Firestore usage store (20 messages, 5 reports and 1,000,000 tokens per user per day)
  • pod-access rules for moved and merged pods
  • a local Firestore "mirror" for testing without touching production
  • a launch-issues checklist

What we knew then

The eval became a real decision tool here. Each experiment wrote down its decision rule before the capture. An example: "adopt k=30 only if the second capture scores at least 1.206 and the gates don't get worse". The numbers were then allowed to say no.

What it cost

Money was never the constraint. A full 90-turn capture cost about $0.20-0.35, and a judge pass $0.20-0.65. The R4 budget was a $30 ceiling (later raised by $10), and single experiments like k=30 cost about $1.18. The constraint was time and attention: 270 commits in a week, across many parallel agent chats.

Where time was wasted (blunt)

  • The answer model was tested very late. The best single improvement in the project, switching to GLM (+0.23 on gold context), came on Sep 26, four days before the release date. A one-day model sweep on gold context in early September would have found it.
  • Grading drift. E4 and every E7 capture answered with the catalogue in the prompt, but the judge rebuilt the prompt without it. This was found on Sep 28, and those verdicts needed re-judging. The harness must grade exactly what the model saw.
  • Skipping human verification of the fixtures saved time, but left question quality resting on agent review alone. That's an honest trade-off under a deadline, and worth saying so in an interview.

Lesson for an ML engineer

  • Calibrate the judge on held-out rows. 0.849 on the tuning rows against 0.25 on unseen ones is classic overfitting of a prompt.
  • Pre-register decision rules. It stops you from cherry-picking the good run.
  • Check that your proxy metric predicts the real one before optimising it. Offline recall looked like a cheap stand-in for answer quality, and it wasn't.
  • Know your noise floor. Two captures of the same configuration differ by about 0.04-0.05. A "gain" smaller than that isn't a gain.

Git lens: worktrees for parallel work

Many chats worked at once, each in its own worktree: a second checkout of the same repository on a different branch, in another folder, sharing one .git. There's no stashing or switching back and forth.

git worktree add ../wt-k30 -b eval/k30 dev   # new folder, new branch, cut from dev
git worktree list                           # see them all (this repo has 40)
git worktree remove ../wt-k30               # clean up after merging

Branch names carried intent (feat/, fix/, docs/, eval/, task/, release/), and a single coordinator chat merged into dev. The cost: 40 worktrees and 45 branches pile up, and STATUS spends lines listing which ones can be removed. Best practice: remove a worktree and delete its branch as soon as the branch merges.

Era 7: Landing

2026-09-29 to 2026-10-01

  • Sep 29: Michael (CER) picked server commit 122136d to ship. Some security fixes were deferred until after launch.
  • Sep 30: the release was merged into CER's develop branches in both upstream repositories and pushed with the user's consent. Release candidate release/rc2 was cut and approved, and the full test suite passed (1,584 tests).
  • Oct 1: Cloud Build was refused for the user's account, so the image was built and tested locally in Docker, then deployed as cer-gilligan (step L5). It now waits on Michael for public access (B1), then a staged rollout (L6-L9).

Where it stands

The Sep 30 date slipped by a few days, but the service is deployed. Known weaknesses are recorded rather than hidden: correctness about 1.16 against a 1.30 floor, refusal wording varying between runs, and several medium-severity answer defects (scores in docs/EVAL_REBUILD.md; module 8 walks through the open defects).

Lesson

  • Good: cutting scope to keep the date ("September 30 holds with reduced scope", Sep 24) and shipping with honest, documented limits.
  • Next time: confirm deploy permissions (Cloud Build, IAM grants) in the first week, not the last. Several launch blockers were access problems, not code problems.

Git lens: commit IDs as release names

A short hash such as 122136d names an exact snapshot that can't change, which branch names can't promise. Release candidates got branches (release/rc1, release/rc2), and the deploy image is tagged with the commit it was built from (cer-gilligan:ddd6292).

git branch --contains 4821679        # which branches include this commit?
git merge-base --is-ancestor A B && echo "A is in B"
git log --oneline release/rc2 ^dev   # commits on rc2 that dev lacks

Best practice: push upstream only to new branches, and get consent before pushing to someone else's repository. This project followed both.

Glossary for this page

ML and eval terms
Token
The unit models read and bill by, roughly ¾ of a word. Cost is input tokens plus output tokens.
Embedding
A list of numbers (here 768) representing a text's meaning. Similar meanings land close together.
Chunk
A slice of a document (with overlap) small enough to embed and retrieve. This corpus has 457.
RAG
Retrieval-augmented generation: search for relevant chunks, put them in the prompt, then answer. Like an open-book exam where you choose which pages to bring.
k (top-k)
How many chunks retrieval returns. The launch uses 20.
Gold context
An eval-only arm that gives the model exactly the right passages. It measures the best the generator can do.
Fixture
One test conversation with its questions, rubric and labels.
LLM judge
A different model that grades answers against a rubric. It has to be calibrated against human grades before you trust it.
Cohen's kappa
Agreement between two graders after removing chance agreement. 1 is perfect, 0 is chance, and around 0.8 or above is strong.
Recall
The share of the needed passages that retrieval actually found.
Spearman correlation
Whether two rankings agree (1 means identical order). 0.29 is weak.
Contamination
Test questions that leak the answer's wording, which makes scores look better than they are.

Check-in questions

Answer these in chat in your own words. There are no trick questions.

  1. The bake-off compared retrieval arms carefully, with fixed thresholds and blind grading. Why were its conclusions still thrown away? Name the single measurement that would have exposed the problem early.
  2. The judge agreed with humans at kappa 0.849 on some rows and 0.25 on others. What's the difference between those rows, and which number should you report?
  3. Offline recall said the reranker was best, but captured answers said it was worse. What does that teach you about proxy metrics?
  4. Why archive old files with a tag instead of just deleting them? What's the trade-off?
  5. About 12 commits were lost in the machine wipe. Which single git habit would have prevented it?

Lessons collected so far (feeds module 10)

  • Measure the generator's ceiling before comparing retrievers.
  • Evaluate on the model you'll ship; run a model sweep early.
  • Size the eval set so each class can support a conclusion.
  • Pre-register decision rules; know the run-to-run noise.
  • Calibrate judges on held-out data; check proxies against the real metric.
  • Settle the corpus with the domain expert before building labels.
  • Confirm deploy access early.
  • Push often; treat upstream code as untrusted.
  • Keep one short living status doc; let git hold history.
