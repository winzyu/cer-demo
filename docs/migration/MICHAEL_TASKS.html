Part A: Before the first deploy

The release owner's account cannot create service accounts, grant IAM, use Secret Manager or create databases, so these steps are yours. Every deploy from L5 onwards waits on them. Do them in order.

A1Check whether an organization policy blocks public invocation

Needed right after the first deployRead-onlyRunbook §2.1 item 6
Why
cer-api calls Gilligan's Cloud Run service, which the release protects with a shared service key rather than Cloud Run sign-in. That needs Cloud Run's invoker check opened, and two organization policies can forbid it.
Where
Cloud Shell
Steps
  1. Run:
    gcloud org-policies describe iam.allowedPolicyMemberDomains --project=$PROJECT --effective
  2. Read the output. If it shows allowedValues listing domains, the domain restriction is on; write down "domain restriction: on". If it prints no allowedValues, or says NOT_FOUND, write down "domain restriction: off".
  3. Run:
    gcloud org-policies describe run.managed.requireInvokerIam --project=$PROJECT --effective
  4. If the output contains enforce: true, write down "invoker check required: on"; otherwise "off".
Done when
You have both answers written down and sent them with A9. If both are "on", ask the organization administrator now for a project exception to either policy, because the release cannot go live without it.

A2Create Gilligan's runtime account

Blocks every deployRunbook §2.1 item 1
Why
Gilligan runs as its own account, with access to its two secrets and its own database only (decision of 2026-09-25).
Where
Cloud Shell
Steps
  1. Create the account:
    gcloud iam service-accounts create cer-gilligan-runtime \
  --project=$PROJECT --display-name="cer-gilligan runtime"
  2. Let the release owner deploy services that run as it:
    gcloud iam service-accounts add-iam-policy-binding $RUNTIME \
  --project=$PROJECT --member=$OWNER --role=roles/iam.serviceAccountUser
  3. Check:
    gcloud iam service-accounts get-iam-policy $RUNTIME --project=$PROJECT
Done when
The last command lists the release owner's account under roles/iam.serviceAccountUser.
Do not
Grant this account any project-wide role. Its only permissions come from A4, A6 and A7.

A4Create the gilligan database and grant the runtime account access to it alone

Blocks every deployRunbook §2.1 item 3Approved by you 2026-09-25
Why
Gilligan keeps only its usage counts (questions and reports per user per day) in its own Firestore database, next to the service, and never touches the customer (default) database (Firestore framework, approved 2026-09-25).
Where
Cloud Shell
Steps
  1. Create the database (takes a minute):
    gcloud firestore databases create --database=gilligan \
  --location=$REGION --type=firestore-native --delete-protection --project=$PROJECT
  2. Grant the runtime account read and write on that database only. The condition limits the role to gilligan:
    gcloud projects add-iam-policy-binding $PROJECT \
  --member=serviceAccount:$RUNTIME --role=roles/datastore.user \
  --condition='expression=resource.name == "projects/conductive-fold-343604/databases/gilligan",title=gilligan-database-only'
  3. If it asks whether to proceed with a conditional binding, answer Y.
  4. Check:
    gcloud projects get-iam-policy $PROJECT --flatten=bindings \
  --filter='bindings.members:cer-gilligan-runtime' \
  --format='table(bindings.role,bindings.condition.expression)'
Done when
The check shows exactly one row: roles/datastore.user with the condition naming databases/gilligan. No row without a condition.
If it goes wrong
If you chose another database name, tell the release owner; it goes into Gilligan's settings.

A5Turn on automatic clean-up of old usage records

Runbook §2.1 item 8No cost
Why
Each usage record carries an expireAt date 90 days after its last update; this policy deletes records after that date.
Where
Cloud Shell, after A4
Steps
  1. gcloud firestore fields ttls update expireAt \
  --collection-group=gilligan_usage --enable-ttl --database=gilligan --project=$PROJECT
  2. Check:
    gcloud firestore fields ttls list --database=gilligan --project=$PROJECT
Done when
A row for gilligan_usage, field expireAt, state CREATING or ACTIVE.
Do not
Put the policy on updatedAt; that would delete live counts.

A6Create the Fireworks key secret

Blocks every deployRunbook §2.1 item 4
Why
Gilligan's model calls use a Fireworks key. For the demo it is the cer-demo development key; CER's own key replaces it later as a new version of the same secret.
Where
Cloud Shell
Steps
  1. Create the empty secret:
    gcloud secrets create cer-gilligan-fireworks-api-key \
  --replication-policy=automatic --project=$PROJECT
  2. Let the runtime account read it, and nobody else:
    gcloud secrets add-iam-policy-binding cer-gilligan-fireworks-api-key \
  --project=$PROJECT --member=serviceAccount:$RUNTIME --role=roles/secretmanager.secretAccessor
  3. Let the release owner add the demo key without sending it to you (they can add versions but not read them):
    gcloud secrets add-iam-policy-binding cer-gilligan-fireworks-api-key \
  --project=$PROJECT --member=$OWNER --role=roles/secretmanager.secretVersionAdder
  4. Check:
    gcloud secrets get-iam-policy cer-gilligan-fireworks-api-key --project=$PROJECT
Done when
secretAccessor lists only cer-gilligan-runtime, and secretVersionAdder lists the release owner. The release owner adds the key and records its version number.

A7Create the service-key secret

Blocks every deployRunbook §2.1 item 5
Why
cer-api sends this key on every call to Gilligan, and Gilligan refuses any call without it. Both services read it from here, so nobody ever sees it.
Where
Cloud Shell
Steps
  1. Generate a random 64-character key and store it in one step; it is never printed:
    openssl rand -base64 48 | tr -d '\n' | gcloud secrets create cer-gilligan-service-key \
  --replication-policy=automatic --data-file=- --project=$PROJECT
  2. Let both services read it:
    gcloud secrets add-iam-policy-binding cer-gilligan-service-key \
  --project=$PROJECT --member=serviceAccount:$RUNTIME --role=roles/secretmanager.secretAccessor
gcloud secrets add-iam-policy-binding cer-gilligan-service-key \
  --project=$PROJECT --member=serviceAccount:$COMPUTE --role=roles/secretmanager.secretAccessor
  3. Check:
    gcloud secrets versions list cer-gilligan-service-key --project=$PROJECT
gcloud secrets get-iam-policy cer-gilligan-service-key --project=$PROJECT
Done when
Version 1 is enabled, and secretAccessor lists both cer-gilligan-runtime and 98242557946-compute@developer.gserviceaccount.com. Tell the release owner the secret name and version 1.

A8Disable the infected cer-ui build trigger

Urgent, securityRunbook §2.1 item 7Walkthrough A7
Why
Trigger 8ad67b17-5439-4507-9718-5b2b5eb4abe9 builds and deploys the live dashboard on every push to the dashboard repository's main, which carries malware. Left on, the next push would replace the dashboard that carries Gilligan's chat page with an infected build. Disabling it stops those builds; it deletes nothing and can be re-enabled.
Where
Cloud console (easiest)
Steps
  1. Open https://console.cloud.google.com/cloud-build/triggers?project=conductive-fold-343604.
  2. At the top, set Region to us-central1. If the trigger is not listed there, set it to global.
  3. Find the trigger whose ID is 8ad67b17-5439-4507-9718-5b2b5eb4abe9 (it builds cer-ui).
  4. Click the three-dot menu at the end of its row and choose Disable. Confirm.
  5. Check in Cloud Shell:
    gcloud builds triggers describe 8ad67b17-5439-4507-9718-5b2b5eb4abe9 \
  --project=$PROJECT --region=$REGION --format='value(name,disabled)'
  6. If that says NOT_FOUND, run it again without --region=$REGION.
Done when
The row shows Disabled, and the check prints the trigger's name followed by True.
Do not
Delete the trigger or run it. The release deploys cer-ui from a clean branch by a different path.

Part B: After Gilligan is deployed

The release owner tells you when each step is due. Both are needed before customers can use Gilligan.

B1Let cer-api reach Gilligan's service

Blocks launchRunbook §2.1 item 6
When
Only after the release owner tells you cer-gilligan exists (they deploy it with no traffic).
Why
Cloud Run refuses unauthenticated callers by default. Gilligan's own service-key check (A7) guards it instead, so Cloud Run's check is opened; anyone without the key is still refused.
Where
Cloud Shell; paste the setup block again first if Cloud Shell has restarted. The option comes from your A1 answers.
Steps
  1. Option 1 (domain restriction off):
    gcloud run services add-iam-policy-binding cer-gilligan \
  --project=$PROJECT --region=$REGION --member=allUsers --role=roles/run.invoker
  2. Option 2 (domain restriction on, invoker check not required):
    gcloud run services update cer-gilligan \
  --project=$PROJECT --region=$REGION --no-invoker-iam-check
  3. Both on: this needs the organization administrator's project exception from A1; tell the release owner, because launch waits for it.
  4. Check:
    gcloud run services get-iam-policy cer-gilligan --project=$PROJECT --region=$REGION
Done when
Option 1: allUsers appears under roles/run.invoker. Option 2: the command completes without an error. Tell the release owner which option you used; they test that a call without the key gets 401.

B2Add CER's own Fireworks key

Needed for launchRunbook §6.4 step 1
When
When the release owner asks, after the demo.
Why
The demo runs on the cer-demo development key. CER's own key replaces it as a new version of the same secret, and the development key is then disabled.
Where
Cloud Shell
Steps
  1. Get CER's Fireworks API key from CER's Fireworks account (https://fireworks.ai, API keys page). Do not paste it anywhere except the next step.
  2. Paste this and press Enter, then paste the key (nothing shows while you paste) and press Enter:
    read -rs KEY && printf %s "$KEY" | gcloud secrets versions add cer-gilligan-fireworks-api-key \
  --data-file=- --project=$PROJECT; unset KEY
  3. Check:
    gcloud secrets versions list cer-gilligan-fireworks-api-key --project=$PROJECT
Done when
A new version number is listed as enabled. Tell the release owner the number; they redeploy Gilligan pinned to it and disable the development key.
