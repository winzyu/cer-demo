Summary

What we are asking for

Gilligan in production currently fails every question, because it calls a Google model that has been retired. The release replaces it with a new answering service that reads the manuals, the customer's own pods and their readings, and can produce a PDF report. While testing it, we also found security holes in CER's existing server, all reproduced on CER's own code; every fix is now written, and the two that change what customers see today ship only if Michael agrees.

The release candidate (rc2) was cut on September 29 and is frozen: the Gilligan service, dashboard and server commits below are the ones that get tested and deployed. Nothing is deployed yet.

  1. Approval to ship the release to production after the demo, as a new version that receives no traffic until it passes a smoke test.
  2. Setup help from Michael on the one-time items listed under What Michael sets up: an account for the new service, the new gilligan database, two secrets and a few permissions. Without them the new service cannot be deployed.
  3. Michael's choice of server version at the demo: with both remaining security fixes, with the spreadsheet-export fix only, or with neither. The other three fixes are in every version. See Server security.
  4. A caveat in place of refusals for weak answers. Gilligan is still below our quality target when it finds the manual pages itself, and it cannot tell which of its own answers are weak. We propose a fixed caveat under every answer that cites the manuals, in place of the refusal rule approved on September 24. It is built into the release, so the demo shows it. See Answer quality.
  5. Smaller confirmations: treating pH readings outside 3 to 12 as implausible sensor readings rather than real water; and, after launch, using the general ranges from CER's source-of-truth v2 when a pod's own limit is missing or reversed, which reverses your September 13 decision. See Decisions.

The path of one question

  1. The dashboard sends the question and the chosen pod to cer-api with the user's login, exactly as before.
  2. cer-api checks the login, loads the chat's earlier messages from (default), and calls cer-gilligan with the service key, the verified user and organization, and the user's own login token.
  3. cer-gilligan refuses the call without the right key, then checks the user's daily counter in the gilligan database.
  4. It rewrites the question into a search query, finds the 20 closest passages in the documents inside its image, and asks the model at Fireworks.
  5. If the answer needs readings, it asks cer-api for them with the user's own token, so the server's organization check applies; it never holds a key of its own for customer data.
  6. It adds the tokens used to the counter and returns the answer, its sources, the data lookups behind it and any report offer.
  7. cer-api saves the message on the chat in (default) and returns it to the page. A report download follows the same path; the PDF is drawn without the model and counts against the 5-a-day limit.

What the data looks like

New: one usage counter per user per UTC day, in gilligan / gilligan_usage. About 200 bytes each.

// document id: <userId>_2026-09-30
{
  userId:         "user-123",
  organizationId: "org-45",
  day:            "2026-09-30",   // UTC day
  questions:      7,              // limit 20
  reports:        1,              // limit 5
  tokens:         214380,         // limit 1,000,000
  updatedAt:      2026-09-30T18:04:11Z,
  expireAt:       2026-12-29T18:04:11Z  // TTL field
}

Each question costs three reads and two writes here. At 300 users all using every allowance, that is about 21,000 reads and 13,500 writes a day, inside Firestore's free daily quota.

Changed: Gilligan chats in (default) / chats. Existing fields are unchanged; the new ones are marked.

{
  user: "user-123",
  assistant: "cer-rag",    // new: marks chat
  creationDate, lastInteraction,
  messages: [{
    question: { text, date, waterData },

      text, date,

      reports: [...],      // new: offers

Old Gemini-era chats have no assistant field, so the new page simply does not list them; nothing is migrated or deleted. The chat list is found with two plain equality filters, so no new index is needed.

Answer quality

How good the answers are

We grade answers on a fixed set of 90 questions, from 0 (wrong) to 2 (fully correct). The target we set before testing is an average of 1.30. All scores below come from the same grader and scoring rules.

SetupAverage scoreMeets 1.30
Previous model, given the right manual pages1.10No
glm-5p3-flash, given the right manual pages1.33Yes
glm-5p3-flash, given the right pages plus the 20 it finds itself1.33Yes
glm-5p3-flash, finding the pages itself (the launch setup)1.16No
Launch setup, questions that need several documents0.83 to 1.00No

The model is good enough, and extra passages do not confuse it: the gap is pages the search misses, mostly on questions that combine several documents. Search improvement continues after launch. Because Gilligan cannot tell which answers are weak, we propose the fixed caveat above rather than refusals. Questions it should decline are refused with a fixed sentence; all eight such test questions were refused correctly at the launch settings, though the wording varied in some other test runs.

Long chats hold up: in five 12-question chats, later answers scored as well as early ones except where the question needed several documents. One fault showed: in long chats, some source links pointed at the wrong passage (13 of 33 late in the chat), because earlier answers' citation markers reached the model. The release removes those markers first; the long-chat run has not been repeated since.

Questions about a customer's own readings use live data rather than manual search. They were tested on a made-up copy of the database: every tool call worked, and the fixes for the problems found are in rc2. The rc2 behaviour itself is first exercised end to end in the demo rehearsal; anything still open is under Open items.

Demo

Demo script

The demo runs on a local copy of rc2 with made-up organizations and pods, so nothing touches customer data. It takes about 40 minutes for Gilligan, then the security fixes side by side (CER's code today against the release), then a quick check that the rest of the dashboard still works. The main steps and what you should see:

  1. 1Log in as a member of one organization and open Gilligan.The disclaimer, the remaining-questions count and only that organization's pods. With one pod, it is already selected.
  2. 2Ask "What does dissolved oxygen measure, and why does it matter for aquatic life?"A plain answer with numbered sources labelled by document title, and the caveat line under it.
  3. 3Ask "What is ORP?", then in the same chat "and how do I calibrate it?"ORP calibration steps from the right manual chapter, not generic calibration advice.
  4. 4Ask "What will the weather be tomorrow?"The fixed refusal sentence, with no caveat.
  5. 5With the pod selected, ask "How is the water this week?"Real readings with the dates covered and the age of the latest reading. No caveat, because the answer rests on readings, not documents.
  6. 6On a pod whose turbidity sensor is stuck, ask "Is the turbidity sensor working?"A likely failed sensor, not clear water, and a referral to CER.
  7. 7On a sea-water pod that reported pH 2.07, ask why the pH crashed that day.The reading is set aside as a likely sensor fault ("may be sensor faults and were left out"); no cause is invented.
  8. 8On a pod that moved, ask for a 60-day report and open the PDF.Only the current site's readings, and the title and summary give the current site's dates, with a note about the earlier location.
  9. 9On a lake pod that absorbed a salt-water pod, ask for its 60-day history.The salt-water history is withheld with a note; no "Action Required" from it.
  10. 10Ask about another organization's pod, by name.A refusal, with no readings and no confirmation that the pod exists.
  11. 11On a pod with a sensor fault, ask "My pod seems broken, who should I contact?"A referral to sales@cleanearthrovers.com or the customer's usual CER contact, with no invented contact.
  12. 12Reload the page and reopen an earlier chat.The saved chats are listed and the earlier answer, sources, caveat and report button come back.
  13. 13Point to the questions-left line."Almost out" at five left; a screenshot shows the limit screen, with sending disabled until the reset time.
  14. 14Log in as a user in a second organization.Only that organization's pods, its own chats and its own separate allowance.

The demo spends real model money: about $1 for a full run of the Gilligan part (about 34 questions and 4 reports, budgeted at $0.02 a question and $0.05 to $0.07 a report, because demo questions lean toward data and reports).

Why 30 users cost about $37 a month, but the ceiling is $144

The two numbers answer different questions. $37 is what we expect if 30 people each ask 10 ordinary questions on each working day. $144 is the most the usage limits can ever let those 30 people spend, even if every one of them pushes Gilligan as hard as it allows, every day. Which limit stops a user first depends on what they ask. A user asking about the manuals uses about 19,000 tokens a question, so they hit the 20-question limit at about 380,000 tokens, or about $0.06 a day. A user asking about readings uses far more: a week of one pod measured about 76,000 tokens, so about 13 such questions reach the token cap; one 30-day comparison across every pod measured about 491,000, so two of those reach it. The token cap exists for that second kind of user.

Two small refinements. The question that crosses the cap is allowed to finish, so a very heavy last question can add up to about $0.07 to that day. And text Fireworks has recently seen costs a fifth as much, which pulls real costs below these figures. Neither changes the picture: at 30 users the worst case is roughly $150 a month (a little more if many days end on a very heavy question), and expected use is about a quarter of that.
