## 1. Summary

`docs/migration/` holds 51 of the 65 tracked documents in `docs/`, plus all 5 captured-output folders, and only a few of them are about the migration.

## 4. Target structure

### 4.1 Folders

- `docs/` (root): `STATUS.md`, `timeline.md`, `SPECS.md`, `STAKEHOLDER_QUESTIONS.md`, `ARCHIVED.md`, and the eval docs `EVAL_REBUILD.md`, `GRADING_GUIDE.md`, `RETRIEVAL_BAKEOFF.md`, `RETRIEVAL_EVAL.md`, `RETRIEVAL_LABELS.md`.
  The first four keep their paths because the flagging rework edits them.
  The eval docs stay because they are cited 37 and 41 times outside `docs/`, including from `eval/` captures and `archive/`, which are never edited; a `docs/eval/` folder would leave those citations broken for good.
- `docs/reference/`: facts about the system and its surroundings that stay true until someone changes them.
  An agent or developer reads these before changing code.
- `docs/runbooks/`: step-by-step procedures, checklists and test scripts, including their explainer pages.
  The user reads these before doing something.
- `docs/plans/`: work not yet done: the backlog, open task lists and live handoffs.
  A plan moves to `records/` when it is finished, or is archived.
- `docs/people/`: what was sent to or prepared for stakeholders (the supervisor, Michael).
  `STAKEHOLDER_QUESTIONS.md` belongs here by role but stays at the root while the flagging rework is open; it can join later.
- `docs/records/`: dated, finished documents: decisions with their reasoning, test results, incidents, finished plans.
  Records are not updated except to add a pointer to what superseded them.
  `timeline.md` remains the chronological index of decisions; records stay flat (29 files) rather than in topic subfolders, so a reader can sort by name or search one folder.
- `docs/captures/`: captured output folders, moved whole and never edited.
  Their internal relative links (`../../../SPECS.md` in two `data-skepticism-runs` READMEs) keep the same depth, so they still resolve.
- `docs/catalogue/`: unchanged; `scripts/renderCatalogueReview.ts` writes it.
- `docs/reflection/` arrives with the `reflection` branch and stays as it is.

### 4.2 Naming convention

- Folders are lowercase.
- Living docs (`reference/`, `runbooks/`, `plans/` backlogs): `TOPIC.md`, no date, no `GILLIGAN_` prefix in new names.
- Records and handoffs: `TOPIC_YYYY-MM-DD.md`, with the date of the event or run.
- Explainer pages: the doc's stem plus `.html` (as `LAUNCH_ISSUES_EXPLAINED.html` is).
- Captures: `<topic>-<date or commit>/`, lowercase kebab.
- Existing files keep their names.
  Code, tests, prompts and `catalogue.json` cite docs by bare name (`MIGRATION_SPEC.md` 34 times, `DEVICE_API.md` 20, `BACKEND_FIELDS.md` 12); a move leaves those findable by name, while a rename breaks every one of them.
  Renaming the undated records and dropping `GILLIGAN_` is offered as decision D3, not recommended.

### 4.3 How a reader finds things

One entry point stays: STATUS "Where things live".
After the moves, the coordinator rewrites that section to one line per folder with its two or three key files; the folder names do the rest.
No `docs/README.md`: the user declined a second map, and with self-describing folders there is nothing for it to add.
`ARCHIVED.md` gains one sentence saying that paths in its older sections predate this reorganization and pointing at the table in section 5.

## 6. Cost of the moves

A file moved from `docs/migration/` to another `docs/<folder>/` keeps its depth, so its links to `../SPECS.md` and other root docs still work.
