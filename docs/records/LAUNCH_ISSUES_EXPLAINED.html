Launch Issues Explained

A study guide for the launch-issues testing. The checklist records results and the walkthrough gives the exact clicks; this page explains what each item is, why it matters and how to tell a pass from a fail. Written 2026-09-28, before any item was run.

0. How to read this

Every item below is explained three ways, in the same order:

  • Analogy: an everyday picture of the problem.
  • Step by step: what the computer actually does, numbered.
  • The test: what we do, what the bug looks like, and what a pass looks like.

Each item also opens with one sentence you could say to Michael, and each section ends with a few "check yourself" questions with hidden answers. Read sections 1 to 4 first: nearly every item depends on them.

1. How the system fits together

Four pieces talk to each other. The one that matters most for security is the server: it is the only piece that decides who may see what.

The single most important idea

The dashboard only shows you your own pods in its menus. That is convenience, not security. Anyone can skip the menus and send a request straight to the server (the browser's Console lets you do this in one line). So the real question for every A item is: when someone asks the server directly for something they shouldn't have, does the server say no?

That is why many tests use the Console helper api(...): it plays the part of a curious or malicious user who types a request the menus would never offer.

2. Account levels

Every user record carries two labels: a role (customer, admin or superadmin) and an organization (the customer company, such as Harbor or Lakeside). Pods belong to an organization too. The main rule of the whole system: you only see your own organization's pods and people. The role decides what you can do inside that wall; only superadmin removes the wall.

Analogy

An office building shared by several companies. A customer has a keycard for their company's floor. An admin has the same keycard plus the power to issue and cancel keycards for their own floor. A superadmin is building security: their master card has no floor printed on it and opens every door.

Step by step, in the server
  1. At login the server hands your browser a token, a signed pass that says who you are, your role and your organization.
  2. Every later request carries the token.
  3. For pod data, a helper called assignOrganization turns the token into a filter: "only pods of organization X".
  4. For a superadmin it deliberately returns no organization, and the pod code reads "no organization" as "no filter".
  5. For user management, separate checks (requireRoles) allow or refuse by role.
Does it matter for testing? Yes

Most A items are "does the wall hold?" tests, and the persona you log in as is the test:

  • Harbor admin is the attacker. For pod data the server treats admins and customers the same, so the strongest non-staff account covers both.
  • Superadmin is a control: they should still get everything. If a fix blocks them too, the fix went too far.
  • Harbor's own pod is the other control: normal use must keep working.

Two odd accounts the tests use on purpose

  • Invited, no password yet (user-harbor-cust-3): an admin invited them by email and they never finished setting up. Used in A5.
  • Orphan, no organization (user-orphan-1): a customer whose organization field is blank. Because "no organization" is also what a superadmin looks like to the pod code, this account accidentally gets the master card. Used in A6.

Everyday personas: Superadmin (user-super-1), Harbor admin, Harbor customer, Lakeside customer (user-lake-cust-1), River Watch customer (user-river-cust-1). All are fake, with addresses ending in mirror.example.invalid.

Check yourself: roles

Why do the A1 and A3 tests log in as Harbor admin rather than Harbor customer?For pod data the server treats the two identically. An admin is the most powerful account that should still be walled in, so if the wall holds for them, it holds for customers.

A fix makes Superadmin get "Device not found" on Lakeside's pod. Pass or fail?Fail. Superadmins are supposed to see every pod; the fix blocked too much.

Why does the orphan user see every pod?Their organization is blank, and blank looks exactly like the superadmin's deliberate "no organization", which the pod code treats as "no filter".

We run several full copies of the system on your machine, all using made-up data, so we can break things safely and for free.

Analogy

A car recall. You test the unrepaired car to show the brake fault happens, then the repaired car to show it no longer does, and you also check the repaired car still steers and starts (that's the U items).

Why two stacks and not one
  1. A "pass" on Release means nothing if the bug never happened in the first place.
  2. So each item gets a before (Current, or our stack without the fix) and an after (Release, with the fix).
  3. Both copies read the same fake database, so the only difference is the code.
Why fake data

The real database is production with real customers and no test copy. The local database (the "emulator") holds 9 made-up organizations, 27 users and 15 pods, and a guard blocks every connection off your machine. We confirmed on 2026-09-27 that nothing was written to production.

4. How a test is judged

Most A tests boil down to a status code, a three-digit number the server sends back with every answer. You see it in the Console result or the browser's Network tab.

200OK, here is the data. Good for your own pod; bad for someone else's.
400Bad request. Our fixes use 400 Device not found to refuse another organization's pod without confirming it exists.
401Not logged in, or login failed. Expected when no token is sent, or on a wrong password.
403Logged in, but your role isn't allowed.
404Not found. Also used on purpose to hide that something exists.
500The server crashed on this request. Never the right answer to anything a user can do.

Each item card below has up to three coloured boxes: red is the bug as it appears today, green is what a pass looks like, amber means undecided or blocked.

5. Glossary

Pod
A floating water-quality sensor. The code calls it a device.
Label
A pod's ID, like dev:100000000000003. It appears in URLs and reports, so it is not a secret and must never be the only thing protecting data.
Readings
Measurements the pod sends, hourly in the fake data: conductivity, pH, dissolved oxygen, temperature and so on.
Period query
The request the dashboard's charts use: "give me the last N days for pod X" (/water/period).
Token
The signed pass the server gives you at login. Requests without one are anonymous.
Console helper
api(method, path), pasted into the browser's developer Console. It sends a request with your login token, so you can ask the server for things the menus don't offer.
Fails open
When a check breaks and lets everyone through, instead of blocking everyone (fails closed). Security checks should fail closed.
Merge, predecessor, survivor
When a pod is replaced, the new pod (survivor) can inherit the old pod's (predecessor's) history, so charts show one continuous record.
Current site
The rule since Sep 25: Gilligan reports only readings from the place the pod is now, never from a previous location.
Report
A PDF water-quality report Gilligan offers to generate, with a status such as "Action Required".
Allowance
Each user gets 20 questions and 5 reports per day on Gilligan.
Control
A check that should succeed, run beside the one that should fail, to prove the test itself works.
Regression
Something that used to work and now doesn't. The U items hunt for these.
Michael demo
Items to show Michael at CER, who decides what goes into the Sep 30 launch (freeze Sep 28).
Plan Q-numbers
Entries in the release plan, such as Q10 (Gilligan answer fixes) or Q11 (CSV fix).

Merged pod history

Background: why pods have "predecessors"

Pods get replaced: a unit fails, a new one goes in at the same spot. So the customer sees one continuous record, the new pod (the survivor) can inherit the old pod's (the predecessor's) readings. The old pod is hidden from lists; its history appears under the new one. Think of a new phone that takes over the old phone's number and photo library.

That raises three questions these items test: whose history may be inherited, who may see it, and whether the old readings still make sense for the new pod.

You inherit a house, and the attic has boxes with no name on them. The executor (CER's supervisor) ruled they're yours. But the building's policy for launch is to keep unlabeled boxes sealed and leave you a note saying so, and neighbours must never get them.

Gilligan answer quality

Background: what a B item tests

B items don't test the wall between companies; they test whether Gilligan's answers are true and clearly stated. Each needs the Mirror, costs a few cents per question, uses a new chat each time (so earlier answers don't influence it), and most have no fix branch yet. The "Q10 fix round" is the planned batch of fixes for B1 to B3.

B1A pod that moved claims the whole period

InternalMustMirror~$0.07

"When a pod has moved, Gilligan correctly uses only the new location's readings, but still tells the customer it covered the whole period."

Analogy

A travel diary titled "60 days in Paris" when you only arrived in Paris 12 days ago. The entries are all genuinely from Paris, but the title misleads, and the only hint is a footnote in a different unit.

Step by step
  1. Lakeside Mobile Buoy moved about 21 km, 12 days before the data ends.
  2. The current-site rule says: report only readings from where the pod is now.
  3. Gilligan follows the rule for the values: roughly the last 12 days.
  4. But the answer, the PDF title and the Summary still say "60 days".
  5. Only the Data Quality row mentions 432 excluded readings, next to 1,728 "readings" that are really 288 rows × 6 measurements, a different unit.
The test

As Lakeside customer on the Mobile Buoy, ask "Summarize the last 60 days", then ask for a 60-day report in another chat. Read the dates everywhere, the Data Quality row, and look for any earlier-site value.

Before
Claims 60 days everywhere; exclusion mentioned only once, in mixed units.
After (Q10)
